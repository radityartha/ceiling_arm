🦾 Single-Arm MoveIt Bringup (standalone test)

Test one arm + tables + MoveIt RViz in one terminal. Does not require the full workcell launch.
1
Run the bringup script (pick the arm IP)
click to copy 
./scripts/start_single_arm.sh 192.168.2.10   # arm 4 (table 2, right)
click to copy 
./scripts/start_single_arm.sh 192.168.2.11   # arm 3 (table 2, left)
Strips the broken rviz2_ws/moveit2_ws overlays, starts arm + tables + move_group in the background, polls for /move_group, then opens RViz. Ctrl+C tears it all down.
2
In RViz — plan & execute
MotionPlanning panel → Planning Group: arm → drag the interactive marker → Plan → Execute
3
Second terminal — drive the tables at the same time (optional)
click to copy 
python3 scripts/table_keyboard.py
⚠ Why a script and not ros2 launch ... launch_rviz:=true? RViz is on a TimerAction inside the combined launch, but the included kortex/move_group sub-launches starve the launch event loop so the timer never fires and no window appears. The script polls for readiness instead. (launch_rviz defaults to false.)
Troubleshooting
Arm not reachableping 192.168.2.10 — check power/Ethernet, arm boots in ~60 s. PC on 192.168.2.x.
Execute silently abortsros2 param set /move_group moveit_manage_controllers false, then retry
Planning fails instantlyA joint is out of bounds — send arm to a safe pose first (clear workspace!)
RViz won't openwhich rviz2 must be /opt/ros/humble/bin/rviz2; the script forces this
Safe-pose command (out-of-bounds recovery)
click to copy 
ros2 action send_goal /joint_trajectory_controller/follow_joint_trajectory \
    control_msgs/action/FollowJointTrajectory \
    "{trajectory: {joint_names: [joint_1, joint_2, joint_3, joint_4, joint_5, joint_6], points: [{positions: [0.0, 0.28, -1.57, 0.0, -1.05, 0.0], time_from_start: {sec: 8, nanosec: 0}}]}}"

🌐 Network — Subnet Fix

Arms are on 192.168.2.x. If PC is on 192.168.1.x, add a secondary IP:

click to copy 
sudo ip addr add 192.168.1.100/24 dev enp1s0

Replace enp1s0 with your actual Ethernet interface name.
