reachability_gng — Quick Start

Growing-Neural-Gas reachability/capability maps for the ceiling workcell (one map per arm, nodes colored by manipulability). Used to seed MoveIt IK and to drive an energy-aware pick / approach — pick which arm + 8-DOF goal by energy, then MoveIt plans collision-aware. Commands only below; full details in README.md.

0 · Build once

cd ~/arm_WS/ceiling_arm/ros2_ws
source /opt/ros/humble/setup.bash
colcon build --packages-select reachability_gng --symlink-install
source install/setup.bash

# GNG maps -> /tmp/arm{1..4}_model.npz  (4 arms built in parallel, ~3 min)
cd ~/arm_WS/ceiling_arm
ros2_ws/src/reachability_gng/build_maps.sh

Tuning knobs are env vars (defaults N=80000 LAM=60 MAX_NODES=3000 EPOCHS=2 BOUNDARY=600), e.g. LAM=160 build_maps.sh → fewer interior nodes. PARALLEL=0 forces sequential; JOB_THREADS bounds each job's threads. /tmp is wiped periodically — rebuild when a node logs cannot load /tmp/armN_model.npz.

B · Topological reach-fusion + approach 4 arms

Detected object → collision-free corridor (Meso diffusion on the GNG reach graph) → energy-ranked arm → approach to a stand-off above the object. Needs A (full) up.

# Terminal 2: perception + depth_cloud + env map + reach_fusion + collision
ros2 launch reachability_gng topo_fusion.launch.py     # seg_source:=yoloe by default
# Terminal 3: interactive target picker (own terminal, reads keyboard)
ros2 run reachability_gng target_cli
#   -> type obj_N / class / index to set target, then 'g' to approach

# or by topic:
ros2 topic pub --once /reach_fusion/set_target std_msgs/msg/String "{data: 'obj_2'}"
ros2 topic pub --once /reach_fusion/execute    std_msgs/msg/Empty  "{}"

Watch for === APPROACH SUCCESS: armN is above the object (EE 0.0XX m …) ===. obj_N is resolved from the object-marker labels (ground truth), IK is multi-seeded, and verification waits for the arm to settle before measuring. Key params: grasp_standoff 0.20 m, ik_timeout 0.3 s, settle_timeout 20 s.

B2 · Static / dynamic topo map reproducible

The env map is geometry, so it is built from depth_cloud (deprojects /rgbd*/depth, no segmentation gate) — it builds even when the detector is blind, and is the real-world RGBD-only path. Split it into a frozen static backbone + a live dynamic remainder so the map stops changing every run yet still tracks moving obstacles.

# 1) capture the STATIC layer once (arms may stay — they are TF self-filtered;
#    clear movable objects for a clean map). Needs depth_cloud running (via B).
ros2 run reachability_gng map_topo_static \
  --ros-args -p max_nodes:=1800 -p max_z:=1.75 -p capture_seconds:=8.0
#    -> /tmp/topo_static.npz

# 2) run two-layer (blue = fixed backbone, green = only dynamic obstacles)
ros2 launch reachability_gng topo_fusion.launch.py \
  static_map:=/tmp/topo_static.npz seg_source:=yoloe \
  bg_dist:=0.15 prune_dist:=0.06 prune_every:=2 \
  max_z:=1.75 self_filter_frames:=20

Launch args: static_map (empty = old all-live map) · bg_dist (drop live pts near a static node; ≥ node spacing) · max_z (crop overhead gantry/arm-mount — set the same for capture and launch) · self_filter_frames (filter each arm over its recent swept path — the sim-time cloud vs wall-clock TF can't be aligned at capture, so raise this if a moving arm flickers green) · self_filter_radius/finger_radius (arm/gripper capsule radii) · topo_cloud (seg_cloud for the old segmented cloud). Add a MarkerArray on /topo_map/static/markers in RViz (already in gng_moveit.rviz as TopoStatic). A new launch auto-kills leftover perception nodes, so a second launch never doubles the map.

B3 · Static topo map on REAL RGBD hardware validated 2026-07-30

Same idea as B2 but for the real 2-camera RealSense rig + real Kinova arms, not the Isaac twin. Use build_topo.sh, not topo_fusion.launch.py, for the capture step.

# 0) check for stray duplicate processes FIRST (biggest source of "looks wrong")
for pid in /proc/[0-9]*; do tr '\0' ' ' < "$pid/cmdline" 2>/dev/null; echo; done \
  | grep -E "realsense2_camera_node|static_transform_publisher|depth_cloud"
# expect exactly 2 camera nodes, 2 camera static_transform_publishers, <=1 depth_cloud

# 1) cameras up + calibrated
ros2 launch reachability_gng extrinsics_view.launch.py with_robot_tf:=false

# 2) real arm+gantry bringup, for self-filter TF -- NOT single_rviz_workcell.launch.py
#    (that one leaves t*_a*_tool_frame disconnected from world entirely)
ros2 launch workcell_moveit_config my_workcell.launch.py \
  use_sim_time:=false use_fake_hardware:=false

# 3) verify self-filter TF resolves for all 4 arms before trusting a capture
for f in t1_a1_tool_frame t1_a2_tool_frame t2_a1_tool_frame t2_a2_tool_frame; do
  ros2 run tf2_ros tf2_echo world $f 2>&1 | grep -A1 Translation | head -2
done

# 5) capture (dual-camera fusion, self-filter on)
cd ros2_ws/src/reachability_gng
CAMS="['rgbd','rgbd2']" OUT=/tmp/topo_static.npz SELF_FILTER=true ./build_topo.sh rgbd

# 6) view
ros2 launch reachability_gng view_topo_static.launch.py map_file:=/tmp/topo_static.npz

Gantry joints have no live encoder feed in my_workcell.launch.py (real Modbus table controller isn't started by it) — they come from config/initial_positions.yaml mock defaults. Confirm those match the gantries' actual physical position (ros2 topic echo --once /joint_states | grep -A1 -E "linear|rotation") before capturing, or that gantry's 2 arms get silently mis-placed in TF and self-filter fails for them with no error. Arms do not need to be tucked away physically — self-filter removes them via TF regardless of pose; movable objects/people do need to be out of frame or beyond MAX_X_FROM_CAMERA (default 2.5 m from each camera's own world-X position). Full detail + troubleshooting: README.md section 8b.
